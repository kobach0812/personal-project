## Friction points

### 1. Disk exhaustion (twice)

The first `xcodebuild test` failure was not a test failure — it was `CASTreeDataStructure/Importer.swift:131: Fatal error: Unable to write data ... due to ioError`, triggered by 132 MiB free at the moment the `xcresult` bundle was finalised. Process exit code was still 0 because the error originated in a simctl diagnostics child process, not `xcodebuild` itself. This is a deceptive failure mode:

- **Symptom**: green-looking exit, but no test summary in stdout, partial `xcresult`, fatal in stderr.
- **Root cause**: Disk pressure during xcresult finalisation.
- **Lesson**: Always check `df -h /` *before* assuming a green exit is a real green.

### 2. Swift Testing emits less to stdout than XCTest

`xcodebuild test` with the `Testing` framework does **not** print `Test Suite started/passed/failed` or `Executed N tests` summaries to stdout the way XCTest does. The only terminal banner is `** TEST SUCCEEDED **`. Numerical pass/fail must be read from the xcresult bundle:

```bash
xcrun xcresulttool get test-results summary --path <result.xcresult>
```

This confirmed 61 passed / 0 failed for the M23-prep run.

### 3. Monitor timeouts on long `xcodebuild`

Two `Monitor` watches hit their timeout while `xcodebuild test` was still in the codesign/launch phase. The cause was `xcodebuild` spending >10 minutes in `IDELaunchParametersSnapshot` retries (a known Xcode 26 quirk on iOS 26.4 simulator boot) — most of the time was *before* tests actually ran. Once tests ran, completion was under 5 minutes.

**Pattern that worked**: monitoring with `until ! kill -0 <pid>; do sleep 5; done` rather than `grep`-ing log content was the more reliable trigger because the test output didn't appear until after the process had nearly finished.

### 4. SourceKit cross-file false positives

Not a session-specific issue but worth noting: SourceKit reliably reports "Cannot find type X in scope" for cross-file references in this project. Only `xcodebuild` truth matters. The session correctly ignored every such report.

- **Plan-before-code discipline held.** When the user picked M23, the response was: audit existing code → write plan → ask for approval. The user said "wait" — that's exactly what the plan-approval gate is for.
- **Todo list stayed lean and accurate.** Six items, transitioned cleanly from `in_progress` → `completed` → final commit gate.

- **Disk cleanup was offered, not unilateral.** Used `AskUserQuestion` with explicit risk levels per option.

### What could be sharper next time

- **Pre-flight check for long builds.** A 5-second `df -h /` and `ls DerivedData` before `xcodebuild test` would have predicted both disk failures.
- **Default to `-resultBundlePath` outside `DerivedData`.** The first attempt let `xcresult` land in DerivedData, which then got purged mid-debugging. Putting it on `/tmp` (as the second attempt did) is more robust.
- **Monitor filters should match terminal states, not just successes.** The first `Monitor` waited for `TEST SUCCEEDED|TEST FAILED|BUILD FAILED` patterns that Swift Testing wasn't going to emit until the very end. Polling the PID is a better terminal signal.
